# Тестовый сервер этапа 1 (T20)

Решения заказчика 23 октября 2026 года (CONFIRMED):

- сервер — существующий Timeweb;
- адрес — test.c4rsys.com;
- коды отправляются с no-reply@c4rsys.com через Amazon SES (Сидней);
- код доставляется через частный репозиторий GitHub.

## Что входит в сборку

| Файл | Назначение |
| --- | --- |
| `docker-compose.prod.yml` | База PostgreSQL, backend (gunicorn), web (Caddy с собранным интерфейсом) |
| `backend/Dockerfile.prod`, `frontend/Dockerfile.prod`, `frontend/Caddyfile` | Рабочие образы; Caddy сам получает сертификат HTTPS |
| `deploy/env.prod.example` | Шаблон настроек и секретов; на сервере копируется в `.env.prod`, который не коммитится |
| `scripts/deploy.sh` | Обновление сервера до текущего `main` |
| `scripts/e2e.sh prod`, `deploy/prod-check.yml` | Проверка этой же сборки у себя или в CI сквозным сценарием |

## Шаги заказчика

Эти шаги требуют вашего аккаунта, оплаты или доступа. Агент их не выполняет.

1. **GitHub.** Создать частный репозиторий (например, `c4rsys`) и сообщить его адрес. Агент добавит его как `origin` и отправит `main` после вашего подтверждения.
2. **Доступ сервера к GitHub.** В настройках репозитория (Deploy keys) добавить ключ сервера только на чтение. Ключ создаётся на сервере командой `ssh-keygen -t ed25519`.
3. **AWS.** Создать пользователя IAM с правами только `ses:SendEmail` и `ses:SendRawEmail` и выпустить для него ключ доступа. Ключ вносится в `.env.prod` на сервере, в чат не пересылается.
4. **DNS в Timeweb.** Добавить запись `A test.c4rsys.com → IP сервера`.
5. **Сервер.** Нужен доступ для проверки, кто занимает порты 80 и 443, есть ли Docker и сколько свободно места.

## Установка на сервере

Сервер — новый чистый облачный сервер Timeweb с Ubuntu 24.04 (решение 23 октября 2026 года; прежний сервер 80.64.17.211 скомпрометирован и не используется). Первичная настройка выполняется один раз от `root`:

```bash
scp deploy/bootstrap.sh root@<IP>:/root/
ssh root@<IP> bash /root/bootstrap.sh
```

Что делает `deploy/bootstrap.sh`:

- ставит Docker из официального репозитория;
- оставляет в файрволе открытыми только SSH, HTTP и HTTPS;
- отключает вход по SSH по паролю, если ключ уже установлен;
- клонирует код в `/opt/c4rsys`;
- создаёт `.env.prod` со сгенерированными секретами, которые не выводятся.

Затем:

1. Ключи пользователя IAM для SES вписываются в `/opt/c4rsys/.env.prod`.
2. Запись A `test.c4rsys.com` направляется на IP сервера.
3. Запуск: `cd /opt/c4rsys && ./scripts/deploy.sh`.

Если репозиторий снова станет частным, серверу понадобится ключ развёртывания только на чтение (Deploy keys в GitHub).

## Внутренний интерфейс системного персонала (блок 11)

Живёт на отдельном поддомене со своим входом (решение В-11.1), тестовый — `staff.test.c4rsys.com`. В `.env.prod`:
поддомен добавляется в `C4R_SITE_ADDRESS` и `DJANGO_ALLOWED_HOSTS`, задаются `C4R_STAFF_HOSTS`, `C4R_STAFF_URL` и контакт
поддержки `C4R_SUPPORT_CONTACT` (см. `deploy/env.prod.example`). Запись A поддомена направляется на IP сервера.

Первый администратор платформы назначается на сервере существующему личному аккаунту (по его c4rsys ID):

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod exec backend \
  python manage.py grant_platform_admin USR-XXXXXXXX --unit Platform
```

Назначение пишется в системный журнал. Следующих сотрудников и их наборы добавляет администратор во внутреннем
интерфейсе. Окончание блокировок по сроку и привилегированных сессий через час, а также уведомления компаниям
выполняет `run_notifications` в сервисе `schedule`.

## Выкладка и откат (пункты 25 и 47 аудита)

Сервер ничего не собирает. CI на каждый коммит в `main` собирает образы `ghcr.io/luckydealer31/c4rsys-backend` и
`c4rsys-web` с тегом коммита (задание `images` в `.github/workflows/ci.yml`). `scripts/deploy.sh` ждёт их
(до 20 минут после push), скачивает и перезапускает сервисы. Caddy до 60 секунд держит запросы, пока
перезапускается backend, поэтому посетители не видят ошибок.

```bash
./scripts/deploy.sh             # текущий main
./scripts/deploy.sh previous    # вернуть версию, выложенную перед текущей
./scripts/deploy.sh <коммит>    # любую версию main, чьи образы собраны
```

Caddy перезапускается только при изменении интерфейса или его настроек: образ веб-части помечен по
содержимому `frontend/`. В это время сайт недоступен несколько секунд. Чтобы проверить простой при
выкладке, во время неё раз в полсекунды запрашивайте `https://test.c4rsys.com/api/health`: ответов, отличных
от 200, быть не должно.

Выложенные версии записываются в `.deploy-history`. На сервере хранятся образы последних десяти. Откат не
отменяет миграции базы. Версия старше миграции, которая что-то удалила, может не запуститься.

Копия перед миграциями (пункт 24 аудита). Если новая версия приносит миграции, `deploy.sh` сначала
останавливает фоновые задачи и делает копию базы и файлов: `/var/backups/c4rsys/<время>-before-<версия>`.
Сайт при этом продолжает работать. Если копию сделать не удалось, выкладка не идёт, текущая версия остаётся.
Если новая версия не запустилась, скрипт печатает две команды возврата с готовыми версией и папкой
копии (`deploy/RECOVERY.md`, случай 1). Данные, внесённые в секунды между копией и перезапуском, в копию
не попадают. Копии перед выкладкой хранятся столько же, сколько ежедневные: 14 дней.

## Наблюдение (пункты 21 и 30 аудита)

- Ошибки сервера уходят в Sentry (`SENTRY_DSN` в `.env.prod`). Sentry пишет о новых ошибках на почту.
- `https://test.c4rsys.com/api/health/full` отвечает 200, только если работают сайт и база и каждый фоновый цикл
  недавно закончил круг (`manage.py heartbeat`). Предел молчания: курсы 4 ч, депозиты 30 мин, расписание 20 мин.
  Иначе адрес отвечает 503 и показывает, какой цикл молчит. Этот адрес раз в минуту проверяет внешний монитор
  (Sentry Uptime) и пишет на почту, если ответ не 200. `/api/health` нужен только Docker и фоновые циклы не
  учитывает.
- Docker проверяет каждую службу (пункт 29 аудита): базу — `pg_isready`, backend — `/api/health`, Caddy —
  отдачу `index.html` с внутреннего адреса `127.0.0.1:8080`, который снаружи контейнера недоступен. Выкладка
  (`up --wait`) ждёт этих проверок, поэтому Caddy, который не отдаёт интерфейс, проваливает выкладку. Фоновые
  циклы проверяются через `/api/health/full`. Сам Docker нездоровый контейнер не перезапускает; перезапуск
  бывает только при падении процесса (`restart: unless-stopped`).

## Журналы (пункт 22 аудита)

На сервере (`C4R_LOG_JSON=1` в `docker-compose.prod.yml`) каждая запись backend, gunicorn и фоновых циклов —
одна строка JSON: `time` (UTC), `level`, `logger`, `message`, `release` (версия кода), `request_id` (тот же,
что в заголовке ответа `X-Request-ID` и в JSON ошибки), `exception` с трассировкой ошибки. Каждый отвеченный
запрос — запись `c4rsys.request` с полями `method`, `path`, `route`, `status`, `duration_ms`; строки запроса
(`?…`) и данных посетителя в ней нет, секретная часть ссылок подписи и установки пароля заменена на `[cut]`.
Успешные проверки `/api/health` от Docker не пишутся. Пример поиска всех записей одного запроса:

```sh
docker compose -f docker-compose.prod.yml --env-file .env.prod logs backend | grep '"request_id": "<ID>"'
```

Сообщения о ходе работы фоновых команд (`Removed …`, `Released …`) остаются обычным текстом. Без
`C4R_LOG_JSON` (разработка) записи пишутся обычным текстом.

## Права процессов (пункт 38 аудита)

- Приложение подключается к базе ролью `c4rsys_app` без прав суперпользователя. Роль владеет базой и её
  таблицами, поэтому миграции работают. Роль и передачу прав делает сервис `db-role`
  (`deploy/db-app-role.sql`) перед запуском backend; пароль `C4R_DB_APP_PASSWORD` `deploy.sh` создаёт сам, если
  его нет. Суперпользователь `c4rsys` остаётся только у контейнера базы; его пароль в контейнеры приложения не
  передаётся.
- Caddy работает от пользователя `caddy` (uid 1000), а не от root; у контейнера одно право — открыть порты.

## Резервные копии (пункт 26 аудита)

`scripts/backup.sh` копирует базу (`pg_dump`, формат custom) и загруженные файлы вместе в
`/var/backups/c4rsys/<время UTC>/`. Дамп проверяется `pg_restore --list`, рядом лежат контрольные суммы
`SHA256SUMS` и коммит кода. `.env.prod` в копию не входит. Таймер ставится один раз:
`bash deploy/backup-timer.sh`.

PROPOSAL (агент, не подтверждено; O13 открыт): каждый день в 20:00 UTC (03:00 по Таиланду), хранить 14 дней.

Решение заказчика 03.11.2026 (CONFIRMED): на тестовом сервере копии хранятся только на самом сервере; вторая
копия в S3 Timeweb отложена (платная, для теста не обязательна). Риск принят: при потере сервера копии пропадут.
Скрипт готов к S3: достаточно создать `/opt/c4rsys/.env.backup` по шаблону `deploy/env.backup.example`
(отдельно от `.env.prod`); тогда копия уходит в хранилище и там тоже хранится 14 дней.

Проверка восстановления (пункт 27 аудита): `scripts/restore-check.sh` раз в неделю, по воскресеньям в 21:00 UTC
(понедельник 04:00 по Таиланду). Скрипт делает свежую копию и восстанавливает её во временную базу рядом с
рабочей. Затем сверяет контрольные суммы, таблицы, миграции и строки каждой таблицы, а также число файлов в
архиве. Копия и проверка отмечаются в `/api/health/full` (`backup`, `restore_check`). Если день прошёл без копии
или восемь дней без успешной проверки, внешний монитор присылает письмо. Оба таймера ставит
`bash deploy/backup-timer.sh`.

Восстановление: `./scripts/restore.sh /var/backups/c4rsys/<время>`. Перед ним скрипт сам сохраняет копию
текущего состояния. Сайт на минуту-две останавливается. Что делать в разных авариях, описано в
[RECOVERY.md](RECOVERY.md).

## Хранение служебных данных (пункт 48 аудита)

Фоновый цикл `schedule` раз в 5 минут удаляет старые служебные записи. Сроки утвердил заказчик 04.11.2026:

| Что | Срок |
|---|---|
| Журнал отправки кодов входа (адрес и IP) | 90 дней |
| Попытки входа, регистрации и подтверждения вместе с их кодами | 30 дней после истечения |
| Сохранённые ответы на повтор запроса (`Idempotency-Key`) | 30 дней |
| Счётчики запросов с одного адреса (пункт 11) | 1 день |

Сессии пользователей не удаляются: их список видит пользователь. Журнал компании не удаляется никогда
(§ 24.4.5). Файлы импорта удаляются через 6 месяцев (§ 22.2.4), выгрузки отчётов через 24 часа.

Журнал каждого контейнера ограничен пятью файлами по 10 МБ, самый старый удаляется (PROPOSAL агента).
Читать журналы: `docker compose -f docker-compose.prod.yml --env-file .env.prod logs --since 1h backend`.
Сервер образы не собирает, поэтому кэша сборки нет. Образы старых версий удаляет `deploy.sh`.

## Проверка приёмки

Критерий T20: сценарий проходит на тестовом сервере. Пока SES в песочнице, коды приходят только на подтверждённые в SES адреса. Поэтому сценарий проходят в браузере с такого адреса.

Не входит в T20 (открыто, O13):

- резервные копии;
- мониторинг;
- автоматическое переключение на резерв.
