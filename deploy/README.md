# Тестовый сервер этапа 1 (T20)

Решения заказчика 23 октября 2026 года (CONFIRMED):

- сервер — существующий Timeweb;
- адрес — test.c4rsys.com;
- коды отправляются с no-reply@c4rsys.com через Amazon SES (Сидней);
- код доставляется через частный репозиторий GitHub.

## Что входит в сборку

| Файл | Назначение |
| --- | --- |
| `docker-compose.prod.yml` | База PostgreSQL, backend (gunicorn), web (Caddy с собранным интерфейсом) |
| `backend/Dockerfile.prod`, `frontend/Dockerfile.prod`, `frontend/Caddyfile` | Рабочие образы; Caddy сам получает сертификат HTTPS |
| `deploy/env.prod.example` | Шаблон настроек и секретов; на сервере копируется в `.env.prod`, который не коммитится |
| `scripts/deploy.sh` | Обновление сервера до текущего `main` |
| `scripts/e2e.sh prod`, `deploy/prod-check.yml` | Проверка этой же сборки у себя или в CI сквозным сценарием |

## Шаги заказчика

Эти шаги требуют вашего аккаунта, оплаты или доступа. Агент их не выполняет.

1. **GitHub.** Создать частный репозиторий (например, `c4rsys`) и сообщить его адрес. Агент добавит его как `origin` и отправит `main` после вашего подтверждения.
2. **Доступ сервера к GitHub.** В настройках репозитория (Deploy keys) добавить ключ сервера только на чтение. Ключ создаётся на сервере командой `ssh-keygen -t ed25519`.
3. **AWS.** Создать пользователя IAM с правами только `ses:SendEmail` и `ses:SendRawEmail` и выпустить для него ключ доступа. Ключ вносится в `.env.prod` на сервере, в чат не пересылается.
4. **DNS в Timeweb.** Добавить запись `A test.c4rsys.com → IP сервера`.
5. **Сервер.** Нужен доступ для проверки, кто занимает порты 80 и 443, есть ли Docker и сколько свободно места.

## Установка на сервере

Сервер — новый чистый облачный сервер Timeweb с Ubuntu 24.04 (решение 23 октября 2026 года; прежний сервер 80.64.17.211 скомпрометирован и не используется). Первичная настройка выполняется один раз от `root`:

```bash
scp deploy/bootstrap.sh root@<IP>:/root/
ssh root@<IP> bash /root/bootstrap.sh
```

Что делает `deploy/bootstrap.sh`:

- ставит Docker из официального репозитория;
- оставляет в файрволе открытыми только SSH, HTTP и HTTPS;
- отключает вход по SSH по паролю, если ключ уже установлен;
- клонирует код в `/opt/c4rsys`;
- создаёт `.env.prod` со сгенерированными секретами, которые не выводятся.

Затем:

1. Ключи пользователя IAM для SES вписываются в `/opt/c4rsys/.env.prod`.
2. Запись A `test.c4rsys.com` направляется на IP сервера.
3. Запуск: `cd /opt/c4rsys && ./scripts/deploy.sh`.

Если репозиторий снова станет частным, серверу понадобится ключ развёртывания только на чтение (Deploy keys в GitHub).

## Внутренний интерфейс системного персонала (блок 11)

Живёт на отдельном поддомене со своим входом (решение В-11.1), тестовый — `staff.test.c4rsys.com`. В `.env.prod`:
поддомен добавляется в `C4R_SITE_ADDRESS` и `DJANGO_ALLOWED_HOSTS`, задаются `C4R_STAFF_HOSTS`, `C4R_STAFF_URL` и контакт
поддержки `C4R_SUPPORT_CONTACT` (см. `deploy/env.prod.example`). Запись A поддомена направляется на IP сервера.

Первый администратор платформы назначается на сервере существующему личному аккаунту (по его c4rsys ID):

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod exec backend \
  python manage.py grant_platform_admin USR-XXXXXXXX --unit Platform
```

Назначение пишется в системный журнал. Следующих сотрудников и их наборы добавляет администратор во внутреннем
интерфейсе. Окончание блокировок по сроку и привилегированных сессий через час, а также уведомления компаниям
выполняет `run_notifications` в сервисе `schedule`.

## Проверка приёмки

Критерий T20: сценарий проходит на тестовом сервере. Пока SES в песочнице, коды приходят только на подтверждённые в SES адреса. Поэтому сценарий проходят в браузере с такого адреса.

Не входит в T20 (открыто, O13):

- резервные копии;
- мониторинг;
- автоматическое переключение на резерв.
