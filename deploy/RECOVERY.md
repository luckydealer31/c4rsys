# План на случай аварии (пункт 49 аудита)

Документ для тестового сервера test.c4rsys.com (80.64.17.211). Все команды выполняются на сервере от `root`
в папке `/opt/c4rsys`:

```bash
ssh root@80.64.17.211
cd /opt/c4rsys
```

OPEN (O13): кто дежурит, кто принимает решение о восстановлении, кому и как сообщать клиентам. Пока это
заказчик.

## Как узнать об аварии

- **Сайт или фоновая задача.** Письмо от Sentry Uptime: монитор раз в минуту открывает
  `https://test.c4rsys.com/api/health/full`. Ответ 503 показывает, что сломалось: `database`, `rates`,
  `deposits`, `schedule`, `backup` или `restore_check`.
- **Ошибка в коде.** Письмо Sentry о новой ошибке.
- **Пользователи пишут, что сайт не работает.**

## Первые пять минут

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod ps     # что запущено
curl -s https://test.c4rsys.com/api/health/full                       # что сломано
df -h /                                                               # место на диске
docker compose -f docker-compose.prod.yml --env-file .env.prod logs --since 15m backend | tail -50
```

Найдите ниже случай, похожий на ваш.

## 1. Сайт сломался после выкладки

Признак: ошибки начались сразу после `./scripts/deploy.sh`.

```bash
./scripts/deploy.sh previous
```

Вернётся версия, выложенная перед текущей. Займёт около минуты, сайт при этом не прерывается. Миграции базы
откат не отменяет. Если новая версия что-то удалила из базы, старая может не запуститься. Тогда переходите
к случаю 3.

## 2. Один сервис упал или завис

Признак: `ps` показывает `exited` или `unhealthy`, либо `/api/health/full` называет молчащую фоновую задачу.

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod restart backend   # или rates, deposits, schedule
```

Если сервис падает снова, смотрите журнал (`logs --since 15m <сервис>`) и ошибку в Sentry.

- Кончилось место (`df -h /` показывает 100 %): `docker system prune -f` убирает остановленные контейнеры
  и ненужные образы. Копии лежат в `/var/backups/c4rsys`, оттуда можно удалить самые старые.
- Не стартует база: смотрите `logs db`. Чаще всего причина тоже в месте на диске.

## 3. Испорчены или удалены данные

Признак: данные пропали или стали неверными, например после ошибки в коде или неверного импорта.

1. Определите, когда данные были ещё правильными. Копии делаются каждый день в 20:00 UTC:
   ```bash
   ls /var/backups/c4rsys
   ```
2. Восстановите копию, сделанную до порчи:
   ```bash
   ./scripts/restore.sh /var/backups/c4rsys/<время>
   ```
   Скрипт попросит ввести `RESTORE`. Перед восстановлением он сам сохранит копию текущего состояния.
   Минуту-две сайт будет отвечать ошибками.
3. Всё, что внесено после этой копии, пропадёт. Если испорчена малая часть, лучше не восстанавливать всю
   базу, а исправить точечно. Копию можно развернуть рядом, на отдельном стенде, и перенести оттуда нужное.
   Так проходили учения 03.11.2026, это работа для разработчика.

## 4. Сервер потерян или взломан

**Важно:** копии сейчас лежат только на этом же сервере (решение 03.11.2026: S3 отложено). Если сервер
потерян целиком, вместе с ним пропадают и копии. Восстановить можно только то, что скачано заранее.
Пока S3 не подключено, раз в неделю скачивайте последнюю копию к себе:

```bash
scp -r root@80.64.17.211:/var/backups/c4rsys/$(ssh root@80.64.17.211 'ls /var/backups/c4rsys | tail -n 1') ~/c4rsys-backups/
```

Если сервер взломан, его не чинят, а заменяют.

1. Новый сервер Ubuntu 24.04 в Timeweb, ваш SSH-ключ. Затем:
   ```bash
   scp deploy/bootstrap.sh root@<новый IP>:/root/ && ssh root@<новый IP> bash /root/bootstrap.sh
   ```
2. В `/opt/c4rsys/.env.prod` впишите ключи, которые не создаются сами:
   - ключи SES (выпустите новые, а старые отзовите в AWS);
   - Sentry DSN;
   - ключи Turnstile;
   - ключ курсов валют;
   - адреса сайтов (`C4R_SITE_ADDRESS`, `DJANGO_ALLOWED_HOSTS` и прочие, по образцу `deploy/env.prod.example`).
3. `./scripts/deploy.sh`, затем `bash deploy/backup-timer.sh`.
4. Перенесите копию на новый сервер и восстановите её:
   ```bash
   scp -r ~/c4rsys-backups/<время> root@<новый IP>:/var/backups/c4rsys/
   ./scripts/restore.sh /var/backups/c4rsys/<время>
   ```
5. В DNS Timeweb направьте записи A для test.c4rsys.com, staff.test.c4rsys.com и system4rent.com на новый IP.
6. При взломе смените всё:
   - пароли и ключи в `.env.prod` (bootstrap создаёт новые сам);
   - ключи AWS, Turnstile и Sentry;
   - SSH-ключи;
   - попросите пользователей сменить пароли.

## 5. Не приходят письма с кодами

Признак: вход и регистрация не работают, в журнале backend ошибки отправки.

- Проверьте в консоли AWS SES (Сидней): не заблокирован ли аккаунт и не исчерпан ли лимит.
- Ключ AWS в `.env.prod` мог быть отозван или истечь. Выпустите новый и выполните `./scripts/deploy.sh`.
